# Tech stack

- `backend/`: FastAPI, with SQLAlchemy Core over Supabase's Postgres, in the `undercover` schema, or SQLite for the tests. The same Core queries run on both. Every API operation has an `operation_id`, a one-line docstring and no optional inputs. Paying a claim is a separate operation that takes the amount. The backend enforces the claim states, the sign-off limit, the two tries on a claim and that nothing is decided or paid twice, so the rules hold whatever an agent does. It works out payouts with UnderCover's payout rules.
- `agent/`: a dispatcher and a claim agent, both LangGraph graphs. The dispatcher, in the style of `labs/week2day4.ipynb`, has no model: it takes a run's claims from the backend and fans out with one `Send` per claim to up to N claim agents at once (`max_concurrency`), each on its own thread. Its worker's `RetryPolicy` waits and retries on LangChain's `ModelRateLimitError` and `ModelTimeoutError`, and its `error_handler` leaves a claim in progress when they don't stop. It runs dispatches over the queue and evaluations of labelled sets. The claim agent is a LangGraph `StateGraph` built by hand, in the style of `labs/week2day3.ipynb`: it works one claim, waits for a handler's sign-off with `interrupt()`, and pays through the backend. Its model node records each reply's tokens and cost, as OpenRouter reports them, through the backend. A `PostgresSaver` of its own for each claim run, on one pool of 4 connections per process, saves every step in Supabase with `durability="sync"`, so a stopped claim carries on from its last step. The agent's own FastAPI service starts dispatches and evaluations, one at a time, and carries a claim on as soon as the backend reports a sign-off. The agent reaches claims, runs, its instructions, the policy wording and the claims manual only through the backend's API. It uses GPT-6 Luna (`openai/gpt-6-luna`) with low reasoning effort by default, or the model in the environment variable `MODEL_NAME` if set, such as `openrouter/free`, with no reasoning effort. It calls OpenRouter through `ChatDeepSeek` from `langchain-deepseek`, because `ChatOpenAI` drops the reasoning OpenRouter sends. `langchain-openrouter` would keep it too, but needs `openrouter` below 1.0, and the project uses 1.2.
- Tracing: Langfuse, with its Python SDK v5 and its LangChain `CallbackHandler`, traces every agent run. Each piece of work on a claim is a trace in the session `<claim id>:<thread id>`, tagged `run-<run id>` with `langfuse_tags` when it is part of a dispatch or evaluation.
- `dashboard/`: React, Vite and TypeScript.
- `e2e/`: Playwright tests.
- `data/`: the business data the backend starts from. Seeding puts the held-out claims and the handlers' decisions from `data/evals/` in tables of their own, which no claim operation reads; the backend scores evaluations from them, and the agent never sees them.

Python 3.12 with uv, all in the root `pyproject.toml`. Node 26. The OpenRouter key is `OPENROUTER_API_KEY` in `.env`, and Langfuse's are `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` and `LANGFUSE_BASE_URL`. Supabase's Postgres is `DATABASE_URL`, through its session pooler; each process uses at most 4 connections, and the claim agents of a process wait for one rather than fail. The backend and the service get `.env` from `npm run dev`, and `uv run -m agent` loads it; the tests never do. LangGraph is at least 1.2.22, whose error handlers catch a failed `Send` task that runs beside others.
