## Running it

- `npm run dev` starts the backend on port 8000 and the dashboard on http://localhost:5173.
- `uv run -m backend.seed` rebuilds the database from `data/`, putting every claim back in the queue.
- `uv run -m agent` starts a run capped at the number of waiting claims: the queue agent plans a to-do list, works the claims one at a time through claim agents, prints a line for each and finishes with a summary. `uv run -m agent --limit 5` caps the run at five claims and leaves the rest waiting. `uv run -m agent CLM-1001` works one claim and prints its line. Both use the real model through OpenRouter: DeepSeek V4.1 Flash, or the model in `MODEL_NAME`.

## Built

- `backend/`: SQLite at `undercover.db` or the path in `UNDERCOVER_DB`. `main.py` creates the app, with `health`, and includes a router for each area. `database.py` holds the schema and a connection for each request, and `seed.py` builds the database from `data/` (never `data/evals/`), on startup when it's missing or with `uv run -m backend.seed`. `claims.py` has the queue and the work on each claim: `list_claims`, `get_claim`, `start_claim`, `record_step`, `list_steps`, `record_decision`, `pay_claim`, `sign_off_claim` and `record_failure`. `records.py` has `get_policy`, `get_claim_history` and `list_handlers`. `documents.py` has what the agent reads: `get_instructions`, and the policy wording and the claims manual section by section with `list_sections`, `search_documents` and `read_section`. `runs.py` keeps runs of the agent over the queue: `start_run` (capped at a number of claims), `write_todos`, `finish_run` with a summary, and `get_latest_run`, which returns null before the first run. A claim moves from waiting to in progress to decided, or to waiting for sign-off when an approval pays over the limit in `company.json`. `record_failure` puts a claim in progress back in the queue with an `error` step, and a second failure moves it to left for a handler. `pay_claim` refuses such a payout with a 403 until a handler signs off, and signing off pays it. The agent's instructions are in `backend/instructions/`: `queue.md` for running the queue and `claim.md` for working a claim, each a goal and what a good result looks like, written from the policy wording and the claims manual. `get_instructions` serves them as `queue` and `claim`, without either document. A test checks that every operation follows the API rules.
- `agent/`, in modules that depend on each other in one direction: `api.py` holds every call to the backend and its base URL, and raises `ApiError` when the backend refuses. `tools.py` holds every tool, each named after the backend operation it calls: the claim agent's `get_claim`, `get_policy`, `get_claim_history`, `list_sections`, `search_documents`, `read_section`, `record_decision` and `pay_claim`, and the queue agent's `list_claims`, `write_todos` and `work_claim`. The queue agent's tools get the run through LangChain's `ToolRuntime`, from a `RunContext` passed as the agent's context, and `work_claim` works one claim at a time and refuses a new claim beyond the run's cap. `harness.py` holds the model (DeepSeek V4.1 Flash with a 120-second timeout), the middleware (`ModelRetryMiddleware` retries a failed call twice, `ModelCallLimitMiddleware` stops an agent at 30 model calls for a claim or 200 for the queue, `ToolErrorMiddleware` hands a backend refusal back to the model, and a missed-claims check sends the queue agent back if it tries to finish with a claim missed), and builds and runs both agents. `work.py` does the work: `work_claim` starts a claim, runs a claim agent, records each step, records a failure if the agent raises or ends without a decision, and reports one line from the backend's record. A section the agent reads is recorded as a `read` step whose first line names the section. `run_queue` starts a run, has the queue agent work it, prints each claim's line and finishes the run with the queue agent's summary, or with one saying it stopped early.
- `dashboard/`: the queue (`/`), with counts by state, including left for a handler, the agent's to-do list for the latest run with its summary, and a line per claim. A claim in full (`/claims/:claimId`), with its policy, earlier claims, the decision and payment, the sections the agent read, the agent's steps as it works, and a sign-off form for a held payout. The agent's instructions for running the queue and for working a claim (`/instructions`), read only. The queue and a claim page refresh every two seconds. Styled to `BRAND.md` in light and dark mode.
- `e2e/`: tests of the three pages, the agent's steps and the sections it read appearing on a claim page, a claim failing twice, the to-do list filling in on the queue page, and a handler signing off a held payout. The tests call the API through the helpers in `e2e/api.ts`. Playwright runs its own backend on port 8001 with `e2e/undercover.db`, and its own dashboard on port 5174, so it can run next to `npm run dev`.

## Last live run

On October 29, 2026, after reseeding, `uv run -m agent --limit 5` with DeepSeek V4.1 Flash ran on its own for 10 minutes 22 seconds. The queue agent planned a to-do list of the five oldest submitted claims and a summary item, ticked each off on the dashboard as it went, and finished with a summary for the handlers. It worked CLM-1001 (approve, $420.00, paid), CLM-1008 (approve, $2,240.00) and CLM-1011 (approve, $1,150.00), both waiting for sign-off with no payment, CLM-1018 (refer) and CLM-1010 (decline). No claim failed. Each claim agent read between 7 and 12 sections of the wording and the manual, and the other 20 claims stayed waiting. These decisions have not been scored against the handlers' decisions in `data/evals/`.

After the code review, the same run with the restructured agent and goal-based instructions took 11 minutes 22 seconds and reached the same five decisions and payouts. Each claim agent read 8 to 12 sections, two also searched the documents, and the backend's refusals of the two held payments reached the agents through `ToolErrorMiddleware`. The queue agent planned its own to-do list, but marked an item for the claims beyond its cap as left for a handler and wrote its summary in Markdown, which the dashboard shows as raw asterisks. The queue instructions now say that left for a handler is only for a claim that failed twice and that the summary is plain text. That change has not yet had a live run.

The pilot's last full run, on September 27, 2026, with `openai/gpt-6-luna`, worked all 25 claims in 2 minutes 47 seconds: 17 approve, 5 decline and 3 refer.
