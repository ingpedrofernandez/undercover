# Status

The claims pilot in `docs/PLAN.md` is built: all six phases are done.

The harness in `docs/PLAN_HARNESS.md` is built: all six phases are done.

## Running it

- `npm run dev` starts the backend on port 8000 and the dashboard on http://localhost:5173.
- `uv run -m backend.seed` rebuilds the database from `data/`, putting every claim back in the queue.
- `uv run -m agent` starts a run capped at the number of waiting claims: the queue agent plans a to-do list, works the claims one at a time through claim agents, prints a line for each and finishes with a summary. `uv run -m agent --limit 5` caps the run at five claims and leaves the rest waiting. `uv run -m agent CLM-1001` works one claim and prints its line. Both use the real model through OpenRouter: DeepSeek V4.1 Flash, or the model in `MODEL_NAME`.

## Built

- `backend/`: SQLite database seeded from `data/` (never `data/evals/`), at `undercover.db` or the path in `UNDERCOVER_DB`, created on startup when missing. Read operations: `health`, `list_claims`, `get_claim`, `get_policy`, `get_claim_history`, `list_handlers`, `list_steps`, `get_instructions`. The policy wording and the claims manual are stored section by section, read with `list_sections`, `search_documents` and `read_section` in `backend/documents.py`. Runs of the agent over the queue are kept in `backend/runs.py`: `start_run` (capped at a number of claims), `write_todos`, `finish_run` with a summary, and `get_latest_run`, which returns null before the first run. Workflow operations: `start_claim`, `record_step`, `record_decision`, `pay_claim`, `sign_off_claim`, `record_failure`. A claim moves from waiting to in progress to decided, or to waiting for sign-off when an approval pays over the limit in `company.json`. `record_failure` puts a claim in progress back in the queue with an `error` step, and a second failure moves it to left for a handler. `pay_claim` refuses such a payout with a 403 until a handler signs off, and signing off pays it. The agent's instructions are in `backend/instructions/`: `queue.md` for running the queue and `claim.md` for working a claim, written from the policy wording and the claims manual. `get_instructions` serves them as `queue` and `claim`, without either document. A test checks that every operation follows the API rules.
- `agent/`: `work_claim(claim_id)` starts a claim, runs the claim agent, records a failure if it raises or ends without a decision, and returns a one-line report built from the backend's record. `run(claim_id, thread_id)` is the claim agent: it fetches its instructions from the backend and works a started claim with eight tools named after backend operations: `get_claim`, `get_policy`, `get_claim_history`, `list_sections`, `search_documents`, `read_section`, `record_decision` and `pay_claim`. It records every tool call, tool result and message as a step, and each section it reads as a `read` step whose first line names the section. The model has a 120-second timeout, `ModelRetryMiddleware` retries a failed call twice, and `ModelCallLimitMiddleware` stops a claim at 30 model calls. `agent/queue.py` is the queue agent: `run_queue(limit)` starts a run and gives the queue agent three tools, `list_claims`, `write_todos` (saved on the run) and `work_claim`, which hands a claim to `work_claim` one at a time and refuses a new claim beyond the cap. A missed-claims check sends the queue agent back to work if it tries to finish while a claim it may take on is still waiting. Its last message becomes the run's summary, and a run whose queue agent fails is finished with a summary saying it stopped early.
- `dashboard/`: the queue (`/`), with counts by state, including left for a handler, the agent's to-do list for the latest run with its summary, and a line per claim. A claim in full (`/claims/:claimId`), with its policy, earlier claims, the decision and payment, the sections the agent read, the agent's steps as it works, and a sign-off form for a held payout. The agent's instructions for running the queue and for working a claim (`/instructions`), read only. The queue and a claim page refresh every two seconds. Styled to `BRAND.md` in light and dark mode.
- `e2e/`: tests of the three pages, the agent's steps and the sections it read appearing on a claim page, a claim failing twice, the to-do list filling in on the queue page, and a handler signing off a held payout. Playwright runs its own backend on port 8001 with `e2e/undercover.db`, and its own dashboard on port 5174, so it can run next to `npm run dev`.

## Last live run

On October 29, 2026, after reseeding, `uv run -m agent --limit 5` with DeepSeek V4.1 Flash ran on its own for 10 minutes 22 seconds. The queue agent planned a to-do list of the five oldest submitted claims and a summary item, ticked each off on the dashboard as it went, and finished with a summary for the handlers. It worked CLM-1001 (approve, $420.00, paid), CLM-1008 (approve, $2,240.00) and CLM-1011 (approve, $1,150.00), both waiting for sign-off with no payment, CLM-1018 (refer) and CLM-1010 (decline). No claim failed. Each claim agent read between 7 and 12 sections of the wording and the manual, and the other 20 claims stayed waiting. These decisions have not been scored against the handlers' decisions in `data/evals/`.

The pilot's last full run, on September 27, 2026, with `openai/gpt-6-luna`, worked all 25 claims in 2 minutes 47 seconds: 17 approve, 5 decline and 3 refer.
