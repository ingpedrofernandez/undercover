# Status

The harness in `docs/PLAN_HARNESS.md` is built: all six phases are done. The code review in `docs/HUMAN_REVIEW_HARNESS.md` has been worked through: the agent is split into `api`, `tools`, `harness` and `work` modules, the backend into a router per area, the instructions state goals rather than steps, and `docs/CODE_STANDARDS.md` and `docs/PROCESS.md` now hold the standards and the review step that would have caught it.

Every agent run is traced in Langfuse.

Durable state in `docs/PLAN_DURABLE.md` is built: all six phases are done. The claim agent works out payouts with UnderCover's payout rules, each claim's work is a Langfuse trace of its own in the claim's session, and the backend's records live in Supabase. The backend treats a repeated decision or payment as done, an approval is decided once it's paid, and a handler's sign-off records who and when, moves the claim back to in progress for the agent to pay, and asks the agent's service on port 8002 to pick it up, which pays it within seconds. If the service can't be reached, the call is logged and the sign-off stands. The claim agent is a LangGraph graph whose every step is saved in Supabase: it stops at an approval the backend holds, and `uv run -m agent` carries a stopped or signed-off claim on from its last saved step.

## Running it

- `npm run dev` starts the backend on port 8000 and the agent's service on port 8002, both with `.env`, so records and checkpoints are in Supabase, and the dashboard on http://localhost:5173.
- `npm run seed` rebuilds the records in Supabase from `data/`, putting every claim back in the queue. `uv run -m backend.seed` does the same for SQLite at `undercover.db` or `UNDERCOVER_DB`.
- `uv run -m agent` first finishes a run that was stopped, with a summary saying so, and carries on every claim in progress, printing a line for each; these don't count against the new run's cap. Then it starts a run capped at the number of waiting claims: the queue agent plans a to-do list, works the claims one at a time through claim agents, prints a line for each and finishes with a summary. `uv run -m agent --limit 5` caps the run at five claims and leaves the rest waiting. `uv run -m agent CLM-1001` carries that claim on if it's in progress, or starts it if it's waiting, and prints its line. Both use the real model through OpenRouter: DeepSeek V4.1 Flash, or the model in `MODEL_NAME`. Both send their traces to the Langfuse project whose keys are in `.env`.

## Built

- `backend/`: Supabase's Postgres in the `undercover` schema when `DATABASE_URL` is set, and otherwise SQLite at `undercover.db` or the path in `UNDERCOVER_DB`; the backend reads no `.env` itself. `main.py` creates the app, with `health`, and includes a router for each area. `database.py` declares the tables with SQLAlchemy Core and builds the engine: on Postgres a pool of at most 4 connections, with `search_path=undercover`. Each request gets a connection that commits if it succeeds, after waiting without a thread for one of four slots. Every query is written with Core, so the same queries run on both. `seed.py` drops and rebuilds our tables from `data/` (never `data/evals/`), on startup when there's no `claims` table or with `npm run seed`, and leaves any other tables in the schema alone. `claims.py` has the queue and the work on each claim: `list_claims`, `get_claim`, `start_claim`, `record_step`, `list_steps`, `record_decision`, `pay_claim`, `sign_off_claim` and `record_failure`. `records.py` has `get_policy`, `get_claim_history` and `list_handlers`. `payouts.py` has `calculate_payout`, which runs the payout rules in `payout_rules.py` (each line's limit, cash, what others paid, the deductible and the benefit's maximum) and says whether the payout needs a sign-off. `settings.py` holds the approval limit from the `settings` table, and `policies.py` finds a policy for both routers that need one. `documents.py` has what the agent reads: `get_instructions`, and the policy wording and the claims manual section by section with `list_sections`, `search_documents` and `read_section`. `runs.py` keeps runs of the agent over the queue: `start_run` (capped at a number of claims), `write_todos`, `finish_run` with a summary, and `get_latest_run`, which returns null before the first run. A claim moves from waiting to in progress to decided. A decline or a referral is decided at once, and an approval once it's paid; an approval over the limit in the `settings` table waits for sign-off first. The same decision again returns the claim, and a different one is refused with a 409. `pay_claim` returns the claim, pays once (a repeat returns the claim), refuses a held payout with a 403 until a handler signs off, and copies the sign-off onto the payment. `sign_off_claim` records who signed off and when, moves the claim back to in progress and, once that's committed, asks the agent's service to resume the claim through `agent_client.py`, the one place that knows its address (`UNDERCOVER_AGENT`, or port 8002). `record_failure` puts a claim in progress back in the queue with an `error` step, refuses a claim with a decision, and a second failure moves it to left for a handler. The agent's instructions are in `backend/instructions/`: `queue.md` for running the queue and `claim.md` for working a claim, each a goal and what a good result looks like, written from the policy wording and the claims manual. `get_instructions` serves them as `queue` and `claim`, without either document. A test checks that every operation follows the API rules.
- `agent/`, in modules that depend on each other in one direction: `api.py` holds every call to the backend and its base URL, and raises `ApiError` when the backend refuses. `tools.py` holds every tool, each named after the backend operation it calls: the claim agent's `get_claim`, `get_policy`, `get_claim_history`, `list_sections`, `search_documents`, `read_section`, `calculate_payout` and `record_decision`, and the queue agent's `list_claims`, `write_todos` and `work_claim`. The claim agent can't pay: the graph does. The queue agent's tools get the run through LangChain's `ToolRuntime`, from a `RunContext` passed as the agent's context, and `work_claim` works one claim at a time and refuses a new claim beyond the run's cap. `harness.py` holds the model (DeepSeek V4.1 Flash with a 120-second timeout, through `ChatDeepSeek`, which keeps the reasoning OpenRouter sends) and the claim graph, built as in `labs/week2day3.ipynb`: a `ClaimState` with the messages, the claim id, the model calls so far and who signed off; an `agent` node that calls the model, records its reply as steps and stops the claim at 30 model calls, counted in the saved state so the cap holds across a restart, with a `RetryPolicy` that retries a failed call twice; LangGraph's `ToolNode`, which hands a backend refusal back to the model as `Refused: ...` and records each result, a section read as a `read` step; a `sign_off` node that waits with `interrupt()`; and a `pay` node that pays through the backend. After the `agent` node the graph reads the claim's status from the backend: held goes to `sign_off`, an approval not yet paid to `pay`, anything else ends. The checkpointer is one `PostgresSaver` per process on a pool of at most 4 connections to Supabase's `undercover` schema, and every run passes `durability="sync"`. `carry_on_input` works out how a thread carries on: from the task when nothing was saved, with the handler's name when it waits at a sign-off the backend has, and otherwise from its last saved step. The harness also holds the queue agent and its middleware (`ModelRetryMiddleware`, `ModelCallLimitMiddleware` at 200 calls, `ToolErrorMiddleware` and the missed-claims check), tracing, and running both agents. `work.py` does the work: `work_claim` starts a waiting claim on a new thread and runs the graph; `carry_on` runs a claim's own thread on from where it stopped; both record a failure if the graph raises or ends without a decision, unless the claim has a decision, and report one line from the backend's record. `catch_up` finishes a stopped run and carries on every claim in progress. `run_queue` starts a run, has the queue agent work it, prints each claim's line and finishes the run with the queue agent's summary, or with one saying it stopped early. `__main__.py` loads `.env` and catches up before a run. `service.py` is the agent's web service: `resume_claim` (`POST /api/claims/{claim_id}/resume`) returns 202 and carries the claim on in a background task, one claim at a time, printing its line, and `health` checks it's running. It opens its checkpointer on startup, and `api.py` reaches the backend at `127.0.0.1`, since on Windows `localhost` cost 2 seconds per connection.
- Tracing: `harness.tracing()` is the one Langfuse handler, passed to every agent run. It is Langfuse's LangChain `CallbackHandler`, which also puts the cost OpenRouter reports for each model call on that call's generation. A run of the queue is one trace, `run-queue`, from the task to the summary: the `queue-agent` with its model calls, its tools and each `work_claim` call. Each claim's work is a trace of its own, `work-claim`, from the claim id to its line, in the Langfuse session `<claim id>:<thread id>`, whether it runs in a queue run or with `uv run -m agent CLM-1001`. `harness.trace_claim` does the work in a fresh context, so a claim agent started inside the queue agent's tool call doesn't nest under it. The tests keep traces in memory and never send them.
- `dashboard/`: the queue (`/`), with counts by state, including left for a handler, the agent's to-do list for the latest run with its summary, and a line per claim. A claim in full (`/claims/:claimId`), with its policy, earlier claims, the decision and payment, who signed off a held payout and when, a note while the agent is paying an approval, the sections the agent read, the agent's steps as it works, and a sign-off form for a held payout. The agent's instructions for running the queue and for working a claim (`/instructions`), read only. The queue and a claim page refresh every two seconds. Styled to `BRAND.md` in light and dark mode.
- `e2e/`: tests of the three pages, the agent's steps and the sections it read appearing on a claim page, a claim failing twice, the to-do list filling in on the queue page, and a handler signing off a held payout. The tests call the API through the helpers in `e2e/api.ts`. Playwright runs its own backend on port 8001 with `e2e/undercover.db`, its own dashboard on port 5174 and a stand-in for the agent's service on port 8003, which records the claims it's asked to resume, so it can run next to `npm run dev`.
